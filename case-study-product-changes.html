Using AI to Catch Unannounced Product Changes

I built a scheduled AI workflow that sends two Slack briefs every week. Docs gets an edit list. Support gets a troubleshooting brief.

One weekly report flagged 11 doc fixes, including an error explanation that had become misleading.

Problem: Hightouch ships quickly, and changes don’t always come with an announcement. When docs and Support find out late, customers hit outdated instructions and get slower answers.

My role: I designed and built the workflow, chose its sources, and shaped each team’s report around the decisions they need to make.

Connecting changes to customer context

I built a scheduled workflow that reviews code changes (GitHub), feature rollouts (LaunchDarkly), support tickets (Pylon), account data, and the Slack channels where Product and Engineering share updates. It connects code changes with rollout information, customer questions, and account context, then uses the same evidence to prepare two different outputs.

Two briefs for two teams

  • Docs gets an edit list. Each finding names the affected page or section, explains what the docs say today, and proposes a change. If a rollout or detail needs verification, the brief identifies who can confirm it.
  • Support gets a troubleshooting brief. Each entry describes who may be affected, what changed, what customers might ask, and what to check or tell them. It flags unconfirmed behavior and points to the owner for follow-up.

Both briefs link to their sources. Teammates can flag useful findings, irrelevant items, and missing guidance.

From a product change to action

One weekly report surfaced a change to HubSpot list syncs: matching began recognizing secondary email addresses and ignoring case. Rows that previously failed could now sync successfully.

Support brief

The brief explained the behavior change, anticipated questions about growing lists, and supplied troubleshooting context and source references.

Docs edit list

The workflow flagged an existing error entry whose explanation had become misleading, giving Docs a specific section to review and update.

What the Docs edit list looks like

One edit list found that several destination guides only told readers to select an audience from a dropdown. It pointed to the change that added another option and suggested updating those steps to say readers can also enter an audience ID.

Another finding flagged a missing guide for an integration whose code had merged. Customer availability was still unclear, so the brief gave Docs a specific question for the owner: is the integration available, and should we publish the guide?

What the Support brief looks like

One brief flagged a rollout rule that could pause free-tier syncs after repeated failures. Here’s an abridged example of what Support received.

Status
Unconfirmed. The rollout rule indicated that a sync could pause after 30 days without a successful run and at least 10 consecutive failures. How many workspaces were affected and whether the rule would stay in place were still unclear.
What customers might ask
Why did my sync schedule turn off?
What to check
If the rule applies, open the latest run, fix the error, then re-enable the schedule. Suggest sync alerts so the customer can catch future failures.
Where to follow up
The brief pointed Support to the rollout rule and its owner, and linked the missing guidance to a proposed Docs update.

Result and iteration

One weekly Docs brief surfaced 11 proposed fixes, including the HubSpot error entry and a destination rename. I use findings like these to decide which pages to review and update. I continue to refine the workflow and its output as teams use it.

To show the core idea outside work, I built a small public prototype, product-change-brief ↗. It reads recent commits from a GitHub repository and uses the Claude API to draft a change brief for documentation and customer-facing teams.
