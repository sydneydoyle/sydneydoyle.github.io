Testing a ClickHouse Quickstart Before Publishing It

I wrote a getting-started guide for the ClickHouse database, built the site with Astro Starlight, and ran every step on a real server before publishing.

Testing surfaced five issues the guide didn’t cover; each is now a troubleshooting entry. The site blocks any change that breaks the build.

Challenge: A quickstart is only useful if it works on a reader's machine. I wanted to learn ClickHouse and Astro at the same time, and to treat the documentation like a product: test the instructions, record what actually goes wrong, and make the site itself catch errors before they reach readers. I built it with Claude Code, directing the agent and reviewing each change.

Testing the instructions, not just writing them

I wrote a five-page guide (overview, quickstart, concepts, troubleshooting, and engineering notes) and kept the first version small: install ClickHouse, load one million rows of synthetic events, and run a first analytical query.

Before publishing, I ran every step against ClickHouse 26.12 on macOS, pasted each SQL snippet into a live server, and replaced placeholder text with real output. Where a page explained why something happens, I ran a query that would expose it if the explanation were wrong. For example, the Concepts page claims the table's sorting key lets ClickHouse skip data. EXPLAIN confirmed it: filtering on the key read 32 of 123 data blocks, and filtering on a non-key column read all 123. That output now appears on the page.

What testing found

Reading the official install script before running it surfaced two behaviors the quickstart didn't mention. Both became Troubleshooting entries with the fix and a "How I found it" line, so readers see the investigation, not just the answer.

A development build by default

The script downloads ClickHouse's latest development build, not a stable release. The entry shows the one setting that switches it to the newest release.

A second tool outside the folder

The script also installs a separate command-line tool into the reader's home directory. The entry explains how to skip it or remove it.

Testing also confirmed a subtle SQL pitfall I had documented: repeated rand() calls return the same value in every column unless each call gets its own argument. The page now shows the real output of both versions.

Making the site check itself

The site deploys to GitHub Pages through a GitHub Actions workflow. A second workflow builds the site on every pull request, so a broken page shows a failing check before it can be merged. I tested that check by deliberately removing a required title field and confirming that Astro's content schema failed the build with a clear error.

Deploying under a subpath also surfaced a classic docs-site bug: Starlight prefixes its own navigation with the base path but not links written in Markdown. I updated every content link and verified that each one resolved in the built site.

Result and iteration

The guide is live, with five Troubleshooting entries found by testing rather than guessed, and every change goes through a build-checked pull request. Next, I plan to test the Docker install path, add automated link checking, and run the SQL snippets in CI so the docs can't drift from what ClickHouse accepts.
