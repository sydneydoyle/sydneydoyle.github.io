Designing Clear, Honest AI Answers

I design what AI tools tell Support teams and customers: the shape of each answer, how it handles uncertainty, and how it explains errors. Then I test those answers against real customer questions.

Support gets weekly AI briefs in one consistent format, every destination guide has a standard Common errors section, and AI answers are graded against real support tickets.

Problem: An AI answer is only useful if someone can act on it. A confident answer that turns out to be wrong costs more than no answer, especially when Support passes it on to a customer.

My role: I designed the output formats, wrote the instructions that shape what the AI says, wrote the error guidance it draws on, and evaluated its answers.

One format Support can scan

My weekly product-change workflow sends Support a brief about each change that could affect customers. Every item follows the same four parts, in the order Support needs them:

Status
How sure we are. This comes first so Support knows how much to trust the rest.
What customers might ask
The question in the customer’s own words, so Support recognizes it when it arrives.
What to check
Steps Support can follow right away, in order.
Where to follow up
The source and the person who owns it, for anything the brief can’t answer.

Saying “we don’t know yet” clearly

I wrote the instructions so the AI labels uncertainty instead of hiding it:

  • When a rollout rule hadn’t been confirmed, the brief marked it Unconfirmed and named what was still unknown, rather than presenting it as fact.
  • When an integration’s code had merged but its availability was unclear, the brief didn’t draft a guide. It gave Docs a specific question for the owner: is it available, and should we publish?
  • My course-drafting command flags features that haven’t been released and asks subject-matter experts for missing context before it writes anything.

Sample dialogue

To show how a brief turns into a customer-facing answer, I wrote this example from the paused-sync brief. The rule behind it was unconfirmed, so the answer says “may have” and doesn’t quote specific limits.

CustomerWhy did my sync schedule turn off?

AssistantYour sync may have been paused automatically after several failed runs in a row. To get it running again:
1. Open the latest run and read the error.
2. Fix the error, then turn the schedule back on.
3. Set up sync alerts so you hear about the next failure right away.

CustomerWill it happen again?

AssistantIt can if the sync keeps failing. With alerts on, you’ll know about a failure as soon as it happens, so you can fix it before the schedule pauses.

Written for this portfolio to show the approach. It isn’t a production transcript.

Why it’s written this way: it opens with the likely cause, hedges only where we were unsure, gives numbered steps in the order the customer will take them, and ends by preventing the next failure.

Error guidance people can act on

Support tickets showed customers getting stuck on the same errors. I made Common errors and Tips and troubleshooting required sections in every destination guide, and published a central error-code reference. Each entry says what the error means and what to do next. For example, the HubSpot guide covers rate limits, missing permissions, and invalid property values. Because AI tools answer from the docs, this guidance also shapes what they tell customers.

Testing answers against real questions

I asked our AI docs tool 18 real questions from support tickets and graded each answer: 6 good, 7 partial, 5 missed. Most misses traced back to gaps in the docs. One led me to an undocumented setting, and I drafted guidance for it. Read how I test and safeguard AI-written docs.
